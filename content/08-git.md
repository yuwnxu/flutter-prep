## Зачем Git на чемпионате

- Работа **сдаётся только через репозиторий**; если проект не собирается из него, оценки нет.
- Эксперты проверяют версию, сохранённую в **вашей ветке спринта**.
- Карточку задачи нужно перенести в «Готово к тестированию» и указать **хэш коммита**.

## Основные команды

```bash
git clone <url>                 # получить репозиторий
git status                      # что изменилось
git add .                       # подготовить все изменения
git commit -m "feat: экран регистрации"
git push                        # отправить на сервер
git pull                        # получить изменения
git log --oneline               # история, видно хэши коммитов
```

## Рабочий цикл спринта

```bash
git checkout main
git pull
git checkout -b sprint-1        # создали ветку для спринта

# ... работа, несколько коммитов, по одному на задачу ...
git add .
git commit -m "feat(uikit): button with all states"
git push -u origin sprint-1     # первая отправка ветки

# в конце спринта: pull request sprint-1 -> main, затем merge
```

| Критерий из таблицы | Что сделать |
|---|---|
| Создана ветка для спринта | `git checkout -b sprint-N` |
| Проект сохранён в ветку и не требует разархивирования | Код лежит в репозитории, **не zip-файл** |
| Выполнен merge / pull request в `main` | PR создан через веб-интерфейс, смёржен и закрыт |

::: tip
Делайте **один коммит на задачу** (карточку). Тогда хэш коммита в карточке однозначно показывает, где выполнена задача. Хэш смотрите в `git log --oneline`.
:::

## Канбан

```
Готово к разработке -> В работе (не более 2) -> Готово к тестированию (+ коммит) -> Завершена (эксперты)
```

Типичные потери: больше двух задач в «В работе», карточка не передвинута, коммит не указан, задача сделана позже закрытия спринта.

## Файл .gitignore

Не коммитьте `build/`, `.dart_tool/`, `.idea/`, ключи и `local.properties`. Flutter создаёт нужный `.gitignore` сам.

## Версионирование библиотек (semver)

Версия `МАЖОР.МИНОР.ПАТЧ`, например `1.2.0`.

| Часть | Когда увеличиваем |
|---|---|
| МАЖОР (1.x.x → 2.0.0) | Несовместимое изменение API |
| МИНОР (1.1.x → 1.2.0) | Новая функция, всё старое работает |
| ПАТЧ (1.2.0 → 1.2.1) | Исправление ошибки |

```bash
# в pubspec.yaml библиотеки
version: 1.0.0

git tag v1.0.0
git push origin v1.0.0
```

Описывайте изменения в `CHANGELOG.md` (в вашем шаблоне там пока `TODO: Describe initial release`, замените его реальным текстом).

## Подключение библиотеки из Git в приложение

```yaml
dependencies:
  uikit:
    git:
      url: https://github.com/<логин>/uikit.git
      ref: v1.0.0            # тег; можно ветка или хэш коммита
  network_layer:
    git:
      url: https://github.com/<логин>/network_layer.git
      ref: v1.0.0
```

Если библиотеки лежат в папке рядом, для разработки удобно:

```yaml
dependencies:
  uikit:
    path: ../uikit
```

::: warn
`ref: main` работает, но после каждого изменения библиотеки приложение получит новую версию неожиданно. Для «независимого версионирования» из задания используйте **теги**.
:::

## Что нужно уметь

- Создать ветку, закоммитить, отправить и смёржить через PR.
- Найти хэш коммита и вставить его в карточку.
- Назвать правила semver и поставить тег.
- Подключить пакет из Git и из локальной папки.

## Подробно: что такое коммит, ветка и merge

Представьте книгу, которую пишут несколько человек.

- **Коммит** — сохранённая «версия страницы» с подписью: что изменили и зачем. К любому коммиту можно вернуться.
- **Ветка** — отдельный черновик. Вы переписываете главу в ветке `sprint-1`, а основной текст (`main`) остаётся нетронутым.
- **Merge** — перенос готовых изменений из черновика в основной текст.
- **Pull request** — «прошу проверить мою главу и принять в книгу». На соревновании это обычно просто формальность, но она оценивается.

```
main:       A ── B ───────────── M (merge)
                  \             /
sprint-1:          C ── D ── E
```

Хороший коммит:

- делает **одну логическую вещь** (одна карточка, один экран);
- имеет понятное описание: `feat(auth): экран авторизации`, `fix(network): обработка таймаута`;
- не содержит мусора (`build/`, `.idea/`, ключи).

## Подробно: pull request пошагово

1. В конце спринта убедитесь, что всё закоммичено: `git status` пустой.
2. Отправьте ветку: `git push -u origin sprint-1`.
3. В веб-интерфейсе (GitHub/GitLab/Gitea) нажмите **Create Pull Request / Merge Request**.
4. Выберите: **откуда** `sprint-1` → **куда** `main`.
5. Заполните название («Спринт 1: UIKit») и описание (кратко, что сделано).
6. Нажмите **Create**, затем **Merge** и подтвердите.
7. Не удаляйте ветку `sprint-1`: эксперту нужно увидеть, что она была.
8. Локально: `git checkout main && git pull`, затем для следующего спринта: `git checkout -b sprint-2`.

Платформа, которую выдадут организаторы, может отличаться, но идея одна.

## Подробно: конфликты слияния

Конфликт возникает, когда две ветки изменили **одну и ту же строку**. Git не знает, какую выбрать, и просит вас.

```
<<<<<<< HEAD
const primary = Color(0xFF00C853);
=======
const primary = Color(0xFF00D95F);
>>>>>>> sprint-2
```

Что делать:

1. Откройте файл, найдите маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
2. Оставьте нужный вариант (или объедините), **удалите** все маркеры.
3. `git add <файл>` → `git commit`.

Как избегать: одна ветка на спринт, один человек, не правьте один и тот же файл в двух ветках.

## Подробно: типичные проблемы с Git

| Проблема | Причина | Решение |
|---|---|---|
| `fatal: not a git repository` | Вы не в папке проекта | `cd` в папку проекта |
| `Updates were rejected` | На сервере есть коммиты, которых у вас нет | `git pull --rebase`, затем `git push` |
| Забыли ветку, работали в `main` | | `git checkout -b sprint-N` (коммиты перейдут вместе) |
| Закоммитили лишнее | Нет `.gitignore` | Добавить файл в `.gitignore`, `git rm --cached <файл>` |
| `detached HEAD` | Переключились на коммит, а не на ветку | `git checkout sprint-N` |
| Не пушится: нет доступа | Неверный логин/токен | Уточнить у организаторов |
| Не помню, что изменилось | | `git status`, `git diff` |

## Практика

1. Создайте репозиторий, ветку `sprint-1`, три коммита, отправьте, оформите PR и смёржите.
2. Создайте конфликт нарочно (две ветки меняют одну строку) и решите его.
3. Поставьте тег `v1.0.0` и подключите пакет по тегу в другом проекте.
4. Найдите хэш последнего коммита и объясните, зачем он нужен в карточке.

## Учимся: навык 1. Ветка, коммит, push, PR

**Сценарий спринта, шаг за шагом (повторите его руками 3 раза):**

1. Перейдите в проект и убедитесь, что вы на `main`: `git status`.
2. Обновите: `git pull`.
3. Создайте ветку спринта: `git checkout -b sprint-1`.
4. Поработали над первой задачей → `git add .` → `git commit -m "feat: кнопка UIKit"`.
5. Следующая задача → снова `add` и `commit` (один коммит на карточку).
6. Отправьте: `git push -u origin sprint-1`.
7. На сайте репозитория: **Create pull request** `sprint-1` → `main` → **Merge**.
8. Обновите локальный `main`: `git checkout main && git pull`.

**Как понять, что всё сделано правильно:** на сайте репозитория видна ветка `sprint-1`, закрытый pull request и коммиты в `main`.

## Учимся: навык 2. Хэш коммита для карточки

1. После коммита выполните `git log --oneline`.
2. Первая строка (самая верхняя) — последний коммит. Скопируйте первые 7 символов (например, `bde42e6`).
3. В карточке задачи вставьте хэш в поле коммита и только после этого переносите её в «Готово к тестированию».

**Важно:** хэш нужен именно того коммита, где задача выполнена. Поэтому делайте **отдельный коммит на каждую карточку**: тогда хэш однозначный, и эксперт проверяет нужную версию.

```bash
git add .
git commit -m "feat: экран авторизации"
git log --oneline -1       # покажет только последний коммит
```

## Учимся: навык 3. Семантическое версионирование и теги

**Формат:** `МАЖОР.МИНОР.ПАТЧ`, например `1.4.2`.

| Что случилось | Что увеличить | Было → Стало |
|---|---|---|
| Исправили ошибку | ПАТЧ | 1.4.2 → 1.4.3 |
| Добавили функцию, всё старое работает | МИНОР (патч в 0) | 1.4.3 → 1.5.0 |
| Изменили API так, что старый код сломается | МАЖОР (остальное в 0) | 1.5.0 → 2.0.0 |

**Выпуск версии:**
1. Поменяйте `version:` в `pubspec.yaml` библиотеки.
2. Запишите изменения в `CHANGELOG.md`.
3. Закоммитьте и смёржите в `main`.
4. `git tag v1.1.0` → `git push origin v1.1.0`.

## Учимся: навык 4. Пакет из Git и из папки

| Ситуация | Как подключить |
|---|---|
| Библиотека в отдельном репозитории (спринт сдаётся по Git) | `git: url + ref` |
| Библиотека лежит рядом на диске (быстро править и проверять) | `path: ../uikit` |

```yaml
dependencies:
  uikit:
    git:
      url: https://github.com/<логин>/uikit.git
      ref: v1.0.0
  network_layer:
    path: ../network_layer
```

**Порядок после правки `pubspec.yaml`:** `flutter pub get`. Если пакет из Git не обновляется, вручную: `flutter pub upgrade uikit`.

**Совет.** При разработке используйте `path`, а перед сдачей переключайтесь на `git` с тегом: так приложение собирается из репозитория, как требует задание.
